# Life OS

A single web app for the day-to-day operational stuff of a life: a
zero-knowledge password manager, a receipts/tax tracker with OCR, and a
fitness tracker — behind one login, sharing one design system.

## Stack

- **Next.js 16** (App Router, TypeScript, Tailwind CSS v4)
- **Neon** (serverless Postgres) + **Drizzle ORM** for schema/migrations/queries
- **Auth.js v5** (Credentials provider, database sessions via the Drizzle adapter)
- **AWS S3** (presigned URLs) for receipt file storage
- **Web Crypto API** (PBKDF2 + AES-256-GCM) for zero-knowledge vault encryption
- **Vitest** for unit tests

## Getting started

```bash
npm install
cp .env.example .env.local   # fill in DATABASE_URL and AUTH_SECRET at minimum
npm run db:push              # or db:generate + db:migrate — see below
npm run db:seed-exercises    # seeds the 500+ exercise library
npm run dev
```

Open http://localhost:3000, sign up, and you're in. S3 and OCR env vars are
optional for local development — everything except the Receipts tab's
upload/OCR flow works without them.

## Environment variables

See `.env.example` for the full list with comments. Required for the app to
boot: `DATABASE_URL`, `AUTH_SECRET`. Required for the Receipts tab:
`S3_BUCKET_NAME`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`,
`OCR_API_URL`, `OCR_API_KEY`.

Generate `AUTH_SECRET` with `npx auth secret` or `openssl rand -base64 32`.

### Plugging in an OCR provider

`lib/ocr/run-ocr.ts` posts the receipt file as `multipart/form-data` to
`OCR_API_URL` with an `Authorization: Bearer OCR_API_KEY` header, and expects
`{ text: string, confidence?: number }` back. If your provider's contract
differs, that's the only file to change — everything downstream (field
parsing, the review UI) only depends on the `OcrResult` shape it returns.

## Database — schema & migrations

All schema lives in `lib/db/schema.ts`. Never edit the database by hand;
generate a migration and commit it:

```bash
npm run db:generate   # writes a new SQL file under drizzle/
npm run db:migrate    # applies pending migrations to DATABASE_URL
```

`npm run db:push` (used above for first-time setup) syncs the schema
directly without generating a migration file — handy locally, but prefer
generate+migrate once you have a team or a production database.

`npm run db:studio` opens Drizzle Studio against your database.

### Exercise library seed

The Fitness tab's global exercise library (500+ entries covering strength,
running, cycling, basketball, and mobility/cardio work) is generated by
`scripts/generate-exercises-json.mjs` into `data/exercises.json` (already
committed), and bulk-inserted by `scripts/seed-exercises.ts`:

```bash
npm run db:seed-exercises
```

Safe to re-run — it matches existing entries by name and only inserts new
ones. To add more exercises, edit the generator script and re-run
`node scripts/generate-exercises-json.mjs` before seeding.

### Workout plan builder

The Fitness tab's Today screen starts with a plan wizard: name → focus scores
(strength, hypertrophy, endurance, flexibility, stability, athleticism, 1–10)
→ weekly mix of gym / home / cardio / recover-and-stretch days → split style
(weekly, bi-weekly A/B, randomized) with optional progressive overload. The
generator (`lib/fitness/generator.ts`) runs in the browser against the
exercise library, is seeded (so "Regenerate" is deterministic), and produces
a 4-week calendar the user reviews and edits before saving. Workout summaries,
plan reviews and the History tab are computed by the pure builders in
`lib/fitness/reports.ts`.

Migration `drizzle/0001_plan_wizard.sql` adds the plan/day columns this needs
(additive only — run `npm run db:migrate`).

### Music library

The Music tab is a personal streaming library: songs, albums, artists,
playlists, a player that keeps playing across tabs (with lock-screen
controls), and generated playlists ("song radio" from seed songs, and mood
mixes like Workout or Chill).

- **Audio lives in object storage, not the database.** Configure any
  S3-compatible bucket with the `MUSIC_STORAGE_*` env vars; Cloudflare R2 is
  recommended (free for 10 GB and no egress fees for streaming). If they're
  unset, the `S3_*` receipts bucket is used. Neon only holds the catalog,
  audio analysis and playlists.
- **Import runs in the browser** (Music → Import → choose a folder in
  Chrome/Edge): each file is hashed (re-runs skip songs already imported),
  its tags and cover art are read with `music-metadata`, the audio is
  analysed (tempo, key, energy, beat strength, brightness —
  `lib/music/analysis.ts`), and the file is PUT straight to the bucket via a
  presigned URL. Nothing large passes through Vercel.
- **Similarity and mixes** (`lib/music/similarity.ts`) combine the audio
  features with genre, artist and era, all computed client-side over the
  library.

R2 setup: create a bucket and an API token with Object Read & Write, then
set `MUSIC_STORAGE_ENDPOINT` (`https://<account-id>.r2.cloudflarestorage.com`),
`MUSIC_STORAGE_BUCKET`, `MUSIC_STORAGE_ACCESS_KEY_ID` and
`MUSIC_STORAGE_SECRET_ACCESS_KEY`. Add a CORS rule on the bucket allowing
`PUT` and `GET` from the app's origin with the `Content-Type` header, or
browser uploads will fail.

Migration `drizzle/0002_music_library.sql` adds the music tables.

**Artwork, release dates, credits and lyrics** (`lib/music/enrich.ts`): tags
in the file are used first; gaps are filled from free public catalogs —
the iTunes Search API (album art, saved into the bucket, and release dates;
shared across an album), MusicBrainz (songwriter / lyricist / producer
credits, rate-limited to ~1 request/second) and LRCLIB (plain and
time-synced lyrics, fetched on demand and cached). Songs are looked up the
first time they're played, or in bulk from Music → Import. While the Music
tab is open, cover art is also filled in the background, one song per album
that has none, paced for Apple's ~20 searches/minute; when a song's title
isn't found the album is searched instead. Release dates
are the song's *original* date: MusicBrainz's `first-release-date` when
known, otherwise the earlier of the catalog date and the file's year tag (so
remasters, alternate mixes and compilations can't make an old song look new);
every song is re-checked in the background, ~1 request/second.
Migration
`drizzle/0003_music_details.sql` adds the columns.

**Duplicates** (`lib/music/duplicates.ts`): besides exact-file matches, the
importer skips likely duplicates by default — same title and main artist
(ignoring case, punctuation, "Remastered"/"Explicit"/"feat." tags) with a
length within 3 seconds; live, remix and acoustic versions stay distinct. The
Import tab lists duplicates already in the library and removes the extra
copies in one go, moving playlist entries, likes and play counts to the copy
that's kept (`POST /api/music/tracks/merge`).

**Missing-songs report** (`lib/music/itunes-library.ts`): open an iTunes
"File → Library → Export Library…" XML in the Import tab and it's compared
with the library on the device (nothing is uploaded): songs already here, and
missing ones grouped by why — on the PC but not imported, in iCloud but not
downloaded, old protected purchases (re-download to get them unlocked), and
Apple Music subscription songs (locked; can't be imported). Exports as CSV. The same export
also carries ratings, play counts, skips, last-played and date-added, loved
songs (→ liked) and playlists over to the matching songs (`POST
/api/music/itunes-sync`); re-running replaces the previously imported plays
(tracked in `imported_play_count`) and updates playlists it created.
Migration `drizzle/0004_itunes_stats.sql` adds the columns.

**Explore** (`lib/music/jamendo*.ts`, `components/music/explore.tsx`): free,
Creative Commons-licensed music from independent artists on
[Jamendo](https://www.jamendo.com) — trending, new releases, genres and
search, streamed straight from Jamendo. Songs whose artists allow downloads
can be saved into the library (`POST /api/music/explore/save` copies the MP3
and cover into the bucket). Needs a free Jamendo API client id
(devportal.jamendo.com) in `JAMENDO_CLIENT_ID`; the tab shows setup steps
until it's set. Jamendo's free API tier is for non-commercial use.

**AI playlists** (`lib/music/ai-mix.ts`, `lib/music/ai-candidates.ts`): Mixes →
"Describe a playlist" sends a free-text request through
[OpenRouter](https://openrouter.ai). One call turns it into criteria (genres,
era, artists, specific songs, energy, tempo); the library is scored against
those locally; a second call picks and orders songs from that shortlist by
number, so it can only choose songs the user owns. Needs `OPENROUTER_API_KEY`;
`OPENROUTER_MODEL` picks the model (default `anthropic/claude-sonnet-5.5`,
falling back to `openrouter/auto` if unavailable).

**Browsing**: a Years tab (decades → years), and multi-select filters on
Songs for decade, year, genre, artist and minimum rating
(`lib/music/facets.ts`).

## Authorization model

Neon is plain Postgres — there's no built-in `auth.uid()`-based row-level
security like Supabase provides. Authorization is enforced entirely in the
application layer: every query helper (`lib/*/queries.ts`) takes the
session's `userId` explicitly and filters on it, and every API route derives
that id from the server-side session (`lib/session.ts`) — never from a
client-supplied value. See `AGENTS.md` §1a for the native Postgres RLS
hardening option if you want defense-in-depth once the schema is stable.

## Password vault: zero-knowledge encryption

The server and database never see a vault entry's plaintext or the key used
to encrypt it:

- The vault's Master Password (separate from your login password) is used
  client-side to derive an AES-256-GCM key via PBKDF2 (600,000 iterations,
  per-user random salt) using the Web Crypto API.
- All encryption/decryption happens in the browser. Only ciphertext
  (`encrypted_blob`/`iv`) and the KDF salt are ever sent to the server.
- The derived key lives in memory only for the tab's session and is cleared
  on lock, idle timeout (10 minutes), or tab close.
- There is intentionally no "forgot master password" recovery — that's the
  zero-knowledge tradeoff. Losing it means losing the vault's contents.

See `lib/crypto/vault-crypto.ts` and its tests
(`lib/crypto/__tests__/vault-crypto.test.ts`) for the implementation and a
round-trip proof.

## Deploying

1. Push to `main` (or your default branch) — Vercel auto-deploys from the
   connected Git repository.
2. Connect Neon from the Vercel project's **Storage** tab (this injects
   `DATABASE_URL` automatically), or paste a pooled Neon connection string
   into **Settings → Environment Variables** manually.
3. Set the remaining environment variables from `.env.example` in Vercel's
   **Environment Variables** settings.
4. Run migrations against the production database as part of your deploy
   step (`npm run db:migrate`) — either locally against the prod
   `DATABASE_URL`, from CI, or as a Vercel build/predeploy step. Run
   `npm run db:seed-exercises` once after the first migration.
